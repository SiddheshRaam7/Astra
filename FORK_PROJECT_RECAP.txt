3. APPLICATION FUNCTIONALITY
===============================================================================

The product is a financial-clarity workspace, not merely a static landing page.
It includes the following major areas:

  - Overview dashboard
  - Cash Flow
  - Goal Planning
  - Money Leaks
  - Financial X-Ray
  - Decision Simulator
  - Finance-management forms
  - Transaction import and bank synchronization
  - AI financial assistant
  - ElevenLabs voice assistant

The Overview displays information such as:

  - Safe-to-spend amount
  - Available checking balance
  - Monthly income
  - Monthly expenses
  - Goals, investments, and emergency contributions
  - Spending pace gauge
  - Recent wallet activity
  - Upcoming payday

Financial calculations are based on recorded user information. The application
reserves money for essentials, planned goals, investing, emergency-fund
contributions, pending transactions, upcoming bills, and a configured cash
buffer before calculating spending room.

The product language deliberately describes financial outputs as planning
estimates rather than guaranteed financial advice.

4. DATABASE WORK
===============================================================================

The main database used by the real application is the user's existing Tiger
Data PostgreSQL service. DATABASE_URL is stored privately in .env.local for local
development and in Vercel's encrypted Production environment for the hosted app.

The Tiger database connection was tested successfully. The migration was
applied and reported that the expected tables and indexes already existed. The
migration is idempotent because it uses CREATE TABLE IF NOT EXISTS, CREATE INDEX
IF NOT EXISTS, and CREATE OR REPLACE VIEW.

Database schema includes:

  - user_profiles
  - financial_snapshots
  - financial_accounts
  - income_sources
  - transactions
  - expense_categories
  - budgets
  - goals
  - recurring_payments
  - emergency_funds
  - scenario_simulations
  - ai_action_logs
  - plaid_items
  - monthly_spending view

The canonical per-user financial state is kept in financial_snapshots. Supporting
tables mirror portions of that state for analytics and domain-specific queries.
Writes use a version field and row locking to protect against conflicting edits.

Plaid access tokens are never stored in plain text. They are encrypted with
AES-256-GCM using TOKEN_ENCRYPTION_KEY before being written into plaid_items.

An additional Neon database was created on Vercel's free plan during an earlier
attempt to create an isolated public demo. It is named fork-public-demo-db. It
was connected to the Vercel project, but the production DATABASE_URL was later
overridden with the real Tiger Data connection after the decision was made to
deploy the authenticated real product. Therefore, production currently uses
Tiger, not the temporary Neon database. The Neon resource can be removed later
if desired, but deletion was not performed automatically.

To move to real banking later:

  1. Apply for Plaid Production access in the Plaid dashboard.
  2. Complete Plaid's company/product/compliance review.
  3. Obtain the Production secret.
  4. Add a PLAID_ENV configuration, preferably supporting sandbox, development,
     and production rather than hardcoding one environment.
  5. Update plaidClient() to select PlaidEnvironments.production when explicitly
     configured.
  6. Replace the Vercel PLAID_SECRET with the production secret.
  7. Update the Link client_name from "FORK · Sandbox" to the production brand.
  8. Test OAuth institutions and any required redirect URI.
  9. Complete privacy-policy, consent, and data-retention requirements before
     inviting real banking users.

Do not simply switch the endpoint to production while retaining a sandbox key;
the credentials and environment must match.

11. SECURITY PROTECTIONS
===============================================================================

The following protections are in place:

  - Production authentication is required through Auth0.
  - Anonymous demo mode is disabled in production.
  - API endpoints use identity checks.
  - State-changing requests validate request origin.
  - Auth cookies are HTTP-only, secure in production, and SameSite=Lax.
  - Session values are HMAC-signed.
  - Plaid access tokens are encrypted at rest using AES-256-GCM.
  - Database state updates use versions and row locks.
  - Financial API responses use Cache-Control: no-store.
  - Security headers include HSTS, X-Frame-Options: DENY,
    X-Content-Type-Options: nosniff, and a restrictive Permissions-Policy.
  - .env.local is ignored by Git.
  - Local .data financial snapshots are ignored by Git.
  - .vercel is ignored by Git.
  - .vercelignore prevents credentials, local financial data, build artifacts,
    logs, and repository metadata from entering CLI deployment uploads.

The .vercelignore file excludes:

   Configure quotas, alerts, and spending limits in each provider dashboard.

   The Auth0 dashboard showed a trial banner with approximately 22 days left at
   the time of setup. Confirm which features FORK uses and whether they are in
   Auth0's free plan. Avoid accidental dependence on a trial-only feature.

6. Add rate limiting.

   Public AI and voice endpoints should have per-user and per-IP rate limits to
   reduce abuse and unexpected API cost.

7. Add production observability.

   Configure structured error reporting and privacy-conscious logs. Never log
   raw access tokens, API keys, authorization codes, financial records, or full
   database connection URLs.

8. Add a privacy policy and terms suitable for financial data.

   This becomes especially important before real Plaid Production access or a
   public launch to users beyond the development team.

9. Add account/data deletion controls.

   Users should eventually be able to disconnect Plaid, revoke stored access
   tokens, export their data, and delete their account and financial data.

10. Confirm product naming.

    The interface is branded FORK, while the proposed public domain is
    dimewilltell.com. Decide whether the product remains "FORK," becomes "A Dime
    Will Tell," or uses one as the company/brand and the other as the product.
